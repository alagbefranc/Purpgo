`purpgo` is the command line interface to Purpgo. It signs in as you, holds one credential per host, and speaks only the public REST API, so it works against the hosted service and against any self-hosted instance you can reach.

```bash
purpgo auth login
purpgo campaign list
purpgo inbox list --unseen
purpgo api "/campaigns?limit=10"
```

<Callout type="info" title="This is not purpgoctl">
There are two CLIs and they answer different questions. `purpgo` is the one you install on your machine to use the product. [`purpgoctl`](/development/purpgoctl/) is the operator's tool: it talks to Postgres directly, runs inside the backend container, and exists for recovery, accounts, health and backups. If you are asking "what is wrong with this install", that is the one you want.
</Callout>

## Install

Pick one. All of them produce the same single binary.

**macOS and Linux**

```bash
curl -fsSL https://purpgo.com/cli.sh | sh
```

Installs to `~/.local/bin`, so it needs no root and no toolchain. The script verifies what it downloaded against the published checksum and installs nothing if they disagree, writes shell completions, and tells you the one line to add to your profile if that directory is not already on your PATH.

**Windows**

```powershell
irm https://purpgo.com/cli.ps1 | iex
```

Installs to `%LOCALAPPDATA%\Purpgo\bin` and adds it to your user PATH. No admin rights.

**Homebrew** (macOS and Linux)

```bash
brew install purpgo/tap/purpgo
```

**Scoop** (Windows)

```powershell
scoop bucket add purpgo https://github.com/purpgo/homebrew-tap
scoop install purpgo
```

**Docker**, for CI or anywhere installing a binary is more trouble than pulling one:

```bash
docker run --rm -e PURPGO_TOKEN ghcr.io/purpgo/purpgo/cli campaign list
```

A container has no browser, so sign in with `PURPGO_TOKEN` rather than `auth login`.

**From source**, if you have Go:

```bash
go install github.com/purpgo/purpgo/cmd/cli@latest
mv "$(go env GOPATH)/bin/cli" "$(go env GOPATH)/bin/purpgo"
```

The package directory is `cmd/cli`, so `go install` names the binary `cli`. Rename it, or use one of the channels above.

**Already have a Purpgo instance?** The binary ships inside the backend image:

```bash
docker compose -p purpgo exec backend purpgo --help
```

### Keeping it current

```bash
purpgo version
purpgo upgrade
```

`upgrade` replaces the binary in place, verifying the download against the release checksums first. When the CLI came from Homebrew or Scoop it says which command to run instead, rather than overwriting a file a package manager owns. The CLI also checks for a new release once a day and mentions it in one line; `PURPGO_NO_UPDATE_CHECK=1` turns that off, and it never runs in CI or when output is piped.

### Installer flags

The install script takes flags after `--`, and every one of them is also an environment variable, so the same install runs from Ansible, cloud-init or a Dockerfile:

```bash
curl -fsSL https://purpgo.com/cli.sh | sh -s -- --dir /usr/local/bin
curl -fsSL https://purpgo.com/cli.sh | sh -s -- --version v1.4.0
curl -fsSL https://purpgo.com/cli.sh | sh -s -- --no-modify-path --no-completions
curl -fsSL https://purpgo.com/cli.sh | sh -s -- --dry-run
curl -fsSL https://purpgo.com/cli.sh | sh -s -- --uninstall
```

| Flag | Variable | What it does |
|---|---|---|
| `--dir PATH` | `PURPGO_INSTALL_DIR` | Where the binary goes. Default `~/.local/bin` |
| `--version TAG` | `PURPGO_CLI_VERSION` | Pin a release instead of taking the newest |
| `--base-url URL` | `PURPGO_CLI_BASE_URL` | Download from an internal mirror of the release assets |
| `--no-modify-path` | `PURPGO_NO_MODIFY_PATH` | Never touch a shell profile |
| `--no-completions` | `PURPGO_NO_COMPLETIONS` | Skip the completion files |
| `--dry-run` | | Print what would happen, change nothing |
| `--uninstall` | | Remove the binary and completions, keep your sign-ins |

`--help` lists them in the terminal. `sh -s -- --help` works through the pipe.

### Reading it before you run it

Piping a script into a shell is worth being careful about, which is why the checksum is published next to it:

```bash
curl -fsSLO https://purpgo.com/cli.sh
curl -fsSLO https://purpgo.com/cli.sh.sha256
sha256sum -c cli.sh.sha256
less cli.sh && sh cli.sh
```

Every release archive is covered by `checksums.txt` on the release, and the installer verifies the archive against it before unpacking. If the two disagree it installs nothing and says so.

### Completions

The installer writes them for your shell. To do it by hand:

```bash
purpgo completion bash > /etc/bash_completion.d/purpgo
purpgo completion zsh  > "${fpath[1]}/_purpgo"
purpgo completion fish > ~/.config/fish/completions/purpgo.fish
```

## Signing in

```bash
purpgo auth login
```

It asks two questions: which instance (the hosted service, or a hostname of your own), and how (a browser approval, or pasting a key you already have).

The browser path shows an eight character code, opens `app.purpgo.com/cli`, and waits. You approve there, choosing which workspace the CLI is signing in to. The client name and machine name on that screen are whatever the terminal reported, so check that the code matches the one your terminal printed. Because approving creates a lasting credential, the screen asks you to confirm it is you (password or second factor) if you have not done so in the last few minutes, the same as creating an API key. The approval creates **one API key named for your machine** (its hostname up to the first dot), which appears under Settings > API keys and is revocable there or with `purpgo auth logout`. The terminal never handles your password, and the browser never handles the key.

```
  Your code: K4TM-9RQD
  Approve at: https://app.purpgo.com/cli?code=K4TM-9RQD

… Waiting for approval (the code expires in 10 minutes)
✓ Signed in to purpgo.com as jane@example.com
  Workspace Acme
```

Non-interactive forms, for a script or an agent:

```bash
purpgo auth login --hostname purpgo.acme.com --web
echo "$PURPGO_KEY" | purpgo auth login --with-token
purpgo auth login --scopes read-only
```

### Scopes

The CLI asks for full access by default. The key it gets never carries more than your role in the chosen workspace allows: the approval screen lists the scopes the key will actually have for that workspace, and anything the CLI asked for beyond your role is left out. If your role allows none of them, the approval is refused with `cli_auth_scopes_role`. Narrow the request with `--scopes`:

```bash
purpgo auth login --scopes read-only
purpgo auth login --scopes read_campaigns,read_contacts,send_campaigns
```

A key's scopes are fixed once created, so widening them means a new key. `purpgo auth refresh --scopes full` runs the sign-in again and revokes the key it replaces, which is why refreshing does not leave a trail of keys behind.

Scope names are the ones in the [permissions reference](/api/permissions/), in either case, with `full` and `read-only` as shorthands.

### Several instances

The CLI holds one credential per host. The `*` in `auth status` is the one commands use.

```bash
purpgo auth login --hostname purpgo.acme.com
purpgo auth status
purpgo auth switch purpgo.acme.com
purpgo campaign list --host purpgo.com   # one command, other host
```

`purpgo auth status` also tells you where the token came from, which is the answer nine times out of ten when a command fails unexpectedly:

```
* purpgo.com
    ✓ signed in as jane@example.com
    - workspace: Acme
    - scopes: all 24
    - api: https://api.purpgo.com
    - token from: /home/jane/.config/purpgo/hosts.yml
    - token: wmbly_ab********wxyz
```

### In CI

Set `PURPGO_TOKEN` and skip the login entirely. It overrides the file and is never written to it.

```yaml
env:
  PURPGO_TOKEN: ${{ secrets.PURPGO_TOKEN }}
  PURPGO_HOST: purpgo.com     # omit for the hosted service
run: purpgo campaign list --json
```

`purpgo auth token` prints the active token and nothing else, for handing to another tool.

## Output

Commands print a table on a terminal and JSON everywhere else, so the same command is readable by a person and parseable by a pipe.

```bash
purpgo campaign list                      # a table
purpgo campaign list > campaigns.json     # JSON, no flag needed
purpgo campaign list --json | jq '.data[].name'
purpgo campaign list --fields name,status
purpgo campaign list --template '{{range .data}}{{.name}}{{"\n"}}{{end}}'
```

`--all` walks the cursor on any list command and merges every page into one response.

## Sending real mail

Anything that puts mail on the wire asks first, and refuses rather than sending when there is no terminal to ask on:

```
$ purpgo campaign start 6f1c…
! `purpgo campaign start` sends real mail. Continue? [y/N]
```

`--yes` is the only way past it, which makes it the flag to grep for in a script review. The commands that behave this way are `campaign start`, `campaign test`, `placement test`, `placement batch-start`, `mailbox send`, `inbox reply`, `inbox compose` and `inbox approve-draft`.

### Examples

```bash
# Create a campaign, add a step, check it, start it
purpgo campaign create --name "Q3 outbound" --daily-limit 40
purpgo campaign add-step CAMPAIGN_ID --subject "Quick question" --wait-after 0
purpgo campaign preflight CAMPAIGN_ID
purpgo campaign start CAMPAIGN_ID

# Mailbox health across the workspace
purpgo mailbox list
purpgo mailbox check MAILBOX_ID
purpgo mailbox edit MAILBOX_ID --daily-limit 40

# Send as a verified Gmail alias, and take the signature from Gmail
purpgo mailbox identity MAILBOX_ID
purpgo mailbox refresh-identity MAILBOX_ID --signature
purpgo mailbox edit MAILBOX_ID --send-as hello@acme.com

# One contact is away: hold their sequence without unsubscribing them
purpgo campaign pause-lead CAMPAIGN_ID CONTACT_ID --until 2026-09-21T17:00:00Z --reason "On holiday"
purpgo campaign resume-lead CAMPAIGN_ID CONTACT_ID

# Two people at one company: copy the second on the first lead's emails
purpgo campaign lead-cc-suggestions CAMPAIGN_ID CONTACT_ID
purpgo campaign set-lead-cc CAMPAIGN_ID CONTACT_ID --cc COLLEAGUE_ID

# The inbox
purpgo inbox list --unseen --limit 20
purpgo inbox thread --email-id EMAIL_ID

# Contacts in and out
purpgo contact create --email jane@example.com --first-name Jane --company Acme
purpgo contact list --all --json > contacts.json
```

## What needs the dashboard

Three things the CLI deliberately does not do, because the API does not let a key do them:

- **Connecting a mailbox.** It needs OAuth consent or a credential form in a browser. `purpgo browse mailboxes` opens the right page.
- **Workspace administration.** Members, roles, invitations, workspace exports and the danger zone are session-only on the API: they depend on a human-bound session and refuse an API key. `purpgo browse members` and `purpgo browse settings` open them.
- **Billing.** Plans, checkout and credits are session-only for the same reason. `purpgo browse billing`.

`purpgo org view` still shows which workspace you are in, and `purpgo team`, `purpgo settings` and `purpgo audit` cover the workspace surface a key can reach.

## Watching events

`purpgo events tail` streams the developer WebSocket into your terminal: the same events the dashboard runs on, printed as they happen. It is the fastest way to see whether an integration is receiving what you think it is, without standing up a public endpoint first.

```bash
purpgo events tail
purpgo events tail --intent EMAIL --intent CAMPAIGN
purpgo events tail --json | jq 'select(.event_type == "EMAIL_REPLIED")'
```

It needs a key with `REALTIME_SUBSCRIBE`; `purpgo auth refresh --scopes full` gets one. The stream, its intents and its event types are documented under [Realtime](/api/realtime/).

## Calling the API directly

`purpgo api` reaches every endpoint, including the ones with no command of their own. Paths are relative to `/v1`.

```bash
purpgo api /me
purpgo api "/campaigns?limit=10" --paginate
purpgo api /contacts -f email=jane@example.com -f first_name=Jane
purpgo api /campaigns/CAMPAIGN_ID -X PATCH -F daily_limit=40
purpgo api /contacts/search -X POST --input filter.json
purpgo api /webhooks/WEBHOOK_ID -X DELETE
```

`-f` keeps a value a string. `-F` guesses the type, so `true`, `false`, `null` and numbers arrive as themselves, `@file` reads a value from a file, `key[sub]=v` nests and repeated `key[]=v` builds an array. `--paginate` follows the cursor, `-i` includes the status and headers, `--idempotency-key` rides the [documented header](/api/authentication/).

## Configuration

Two files under `~/.config/purpgo` (or `XDG_CONFIG_HOME`, or `PURPGO_CONFIG_DIR`):

- `hosts.yml`, one credential per host, written 0600
- `config.yml`, preferences and aliases

Signing in records the instance's own API and dashboard URLs alongside the credential, taken from what the instance reports, so `browse` and `events tail` work on a self-hosted layout without anyone configuring a second address.

```bash
purpgo config list
purpgo config set output json      # default to JSON even on a terminal
purpgo config set confirm always   # confirm every write, not only sends
purpgo config set browser firefox
```

### Aliases

```bash
purpgo alias set hot "campaign list --status active"
purpgo hot --json
```

Anything you type after the alias is appended, so an alias is a starting point rather than a fixed command.

### Environment

| Variable | What it does |
|---|---|
| `PURPGO_TOKEN` | The API key to use. Overrides `hosts.yml` and is never written to it |
| `PURPGO_API_KEY` | The same thing under the name `purpgoctl` uses |
| `PURPGO_HOST` | Which signed-in host to use |
| `PURPGO_API_URL` | The API base URL, when it is not derivable from the host |
| `PURPGO_CONFIG_DIR` | Where the two files live |
| `PURPGO_NO_UPDATE_CHECK` | Never check for a newer release |
| `NO_COLOR` | Turns colour off, as everywhere else |

## Exit codes

| Code | Meaning |
|---|---|
| `0` | It worked |
| `1` | The command failed, or you declined a prompt |
| `2` | The command line was wrong, or an answer was needed with no terminal to ask on |
| `4` | Not signed in, or the credential was rejected or lacks a scope |

Every API failure prints the response's machine-readable `code` and `request_id` to stderr, so a script can branch without reading prose.
